# API Example

A production-oriented Go REST API starter showing the same layered patterns used by larger services without carrying product-specific business logic.

The included `documents` example demonstrates JWT authentication, PostgreSQL with SQLC, Go-struct migrations, streaming local/S3 storage, a Redis worker queue, authorization, soft deletion, structured errors, and infrastructure-free unit tests.

## Requirements

- Go 1.25+
- Docker with Docker Compose
- `sqlc`, `golangci-lint`, and Air (`make install-tools`)

## Quick start

```bash
cp .env.example .env
make deps
make install-tools
make sqlc-generate
make docker-up
make migrate-up
make test
make dev
```

The server listens on `http://localhost:8080`. Run the worker separately:

```bash
make worker
```

Use `make help` to see every supported command.

## API contract

`api-spec.yml` is the authoritative OpenAPI contract for the HTTP API. Every
route, request, response, authentication, or public schema change must update
`api-spec.yml` in the same change. Keep handler tests aligned with the contract
and review the spec as part of `make test` verification.

## API example

Register and capture the access token from the response:

```bash
curl -X POST http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","password":"password-123"}'
```

Upload and list documents:

```bash
curl -X POST http://localhost:8080/api/v1/documents \
  -H 'Authorization: Bearer ACCESS_TOKEN' \
  -F 'file=@./example.pdf;type=application/pdf'

curl http://localhost:8080/api/v1/documents?page=1\&page_size=20 \
  -H 'Authorization: Bearer ACCESS_TOKEN'
```

Uploads use S3 object storage. The service generates an opaque key, uploads the
stream to S3, and persists that key in `documents.storage_key`. Successful create,
get, and list responses expose a client-facing `url` composed as
`CDN_URL + "/" + storage_key`; the raw storage key is not returned as a separate
API field:

```json
{
  "id": 42,
  "owner_id": 7,
  "original_name": "example.pdf",
  "media_type": "application/pdf",
  "size_bytes": 12480,
  "url": "https://cdn.example.com/documents/7/31ed1d5f5f684cf995a4b6f86b648881",
  "status": "pending",
  "created_at": "2026-09-04T09:00:00Z",
  "updated_at": "2026-09-04T09:00:00Z"
}
```

The worker moves uploaded documents through `pending → processing → ready`, or to `failed` with a bounded diagnostic message. Jobs that exhaust the configured attempt count move to the dead-letter list.

## Configuration

All configuration comes from environment variables. `.env` is supported locally and is intentionally ignored by Git.

- `APP_*`: application name, environment, port, and debug mode
- `DB_*`: PostgreSQL connection and pool settings
- `REDIS_*`: Redis connection, queue names, and maximum job attempts
- `JWT_*`: signing secret, issuer, audience, and token expiry durations
- `STORAGE_*`: driver, upload limit, media allowlist, and local root
- `CDN_URL`: public CDN origin used to build document URLs (required for S3)
- `S3_*`: S3 region, bucket, optional endpoint, credentials, and path-style mode
- `LOG_*`: log level and `json`, `text`, or `colored_text` format
- `CORS_ALLOWED_ORIGINS`: comma-separated browser origin allowlist

Replace `JWT_SECRET` with at least 32 cryptographically random characters in every deployed environment.

## Storage drivers

The upload contract uses S3. The checked-in `.env.example` targets the local
MinIO service, and `make docker-up` starts it together with PostgreSQL and Redis.
The MinIO initialization container creates the bucket and enables public reads
so its URL can stand in for a CDN during local development. You can also start
that Compose profile directly:

```bash
docker compose --profile s3 up -d
```

For isolated storage-adapter development, local filesystem storage remains
available:

```dotenv
STORAGE_DRIVER=local
STORAGE_LOCAL_ROOT=./data
```

For AWS S3 or an S3-compatible service:

```dotenv
STORAGE_DRIVER=s3
S3_REGION=us-east-1
S3_BUCKET=api-example
S3_ENDPOINT=http://localhost:9000
S3_USE_PATH_STYLE=true
CDN_URL=https://cdn.example.com
```

Object keys are generated by the service and never derived directly from client filenames. Deleting a document soft-deletes its database metadata but intentionally retains the stored object. Physical purge and retention policy are application-specific and are not included in this starter.

## Migrations and SQLC

Migration executors live in `migrations/list/`. This starter uses Go migrations rather than standalone `*.up.sql` and `*.down.sql` files, so each migration can execute several related statements inside one PostgreSQL transaction.

### Migration contract and ordering

Every migration implements:

```go
type Migratable interface {
    GetName() string
    Up(context.Context, pgx.Tx) error
    Down(context.Context, pgx.Tx) error
}
```

Files and names use the same double-digit sequence:

```text
migrations/list/
├── 01_create_auth_schema.go
├── 02_seed_roles.go
├── 03_create_documents.go
├── 04_create_projects.go
├── migrations.go
└── schema/
```

`GetName()` in `04_create_projects.go` must return exactly `04_create_projects`. Append the migration to `GetMigrations()` in `migrations/list/migrations.go`; slice order is execution order. Registry tests reject malformed names, duplicate names, wrong ordering, or a numbered migration file missing from the registry.

Never edit a migration after it has reached a shared environment. Add a new numbered migration for every subsequent change.

### How the runner works

The migration runner creates a `migrations` changelog table automatically. For each pending migration, `up`:

1. Starts a PostgreSQL transaction.
2. Calls the migration's `Up` method.
3. Inserts its exact name into the changelog.
4. Commits both schema work and changelog entry together.

If any statement or changelog write fails, the transaction is rolled back and later migrations do not run. A migration already recorded in the changelog is skipped, so rerunning `up` is safe.

`down N` selects the latest `N` recorded migrations. For each one it starts a transaction, calls `Down`, removes the changelog entry, and commits. Seed migrations may intentionally use a no-op `Down` when deleting stable seed rows could break foreign keys or application data. Treat rollback as an operationally sensitive action: review the exact `Down` code and back up production data before running it.

### Commands

| Command | Purpose | Database required |
| --- | --- | --- |
| `make migrate-validate` | Validate names and uniqueness without executing SQL | No |
| `make migrate-status` | Show every registered migration as `PENDING` or `EXECUTED` | Yes |
| `make migrate-dry-run` | Inspect pending/executed state without applying or reverting SQL | Yes |
| `make migrate-check` | Verify the database connection and changelog table | Yes |
| `make migrate-up` | Apply every pending migration in registry order | Yes |
| `make migrate-down steps=1` | Revert the latest recorded migration | Yes |

Set `ENV=staging` or another environment name to load `.env.<environment>` before running a database command:

```bash
make migrate-status ENV=staging
make migrate-up ENV=staging
```

### Adding a migration

Create `migrations/list/04_create_projects.go`:

```go
package list

import (
    "context"

    "github.com/jackc/pgx/v5"
)

type CreateProjects struct{}

func (*CreateProjects) GetName() string { return "04_create_projects" }

func (*CreateProjects) Up(ctx context.Context, tx pgx.Tx) error {
    _, err := tx.Exec(ctx, `
CREATE TABLE IF NOT EXISTS projects (
    id BIGSERIAL PRIMARY KEY,
    owner_id BIGINT NOT NULL REFERENCES users(id),
    name VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS projects_owner_id_idx
    ON projects (owner_id, id DESC)
    WHERE deleted_at IS NULL;
`)
    return err
}

func (*CreateProjects) Down(ctx context.Context, tx pgx.Tx) error {
    _, err := tx.Exec(ctx, `DROP TABLE IF EXISTS projects`)
    return err
}
```

Register it:

```go
func GetMigrations() []Migratable {
    return []Migratable{
        &CreateAuthSchema{},
        &SeedRoles{},
        &CreateDocuments{},
        &CreateProjects{},
    }
}
```

Then update the expected order in `migrations/list/migrations_test.go`.

### Keeping migration DDL and SQLC schema aligned

Go migration files are the runtime source of schema changes. SQLC does not execute them; it parses the plain schema files under `migrations/list/schema/`. Therefore every table, column, constraint, and type added by a Go migration must also be mirrored in the appropriate schema file.

For the project example:

1. Add the runtime DDL in `04_create_projects.go`.
2. Add the matching `CREATE TABLE projects` definition to `migrations/list/schema/`.
3. Add parameterized queries to `internal/repository/queries/projects.sql`.
4. Run `make sqlc-generate`.
5. Use the generated methods from the repository adapter; never edit generated files.
6. Run `make migrate-validate`, `make sqlc-vet`, and `make test`.

Migration DDL commonly uses `IF EXISTS` and `IF NOT EXISTS` for operational safety. SQLC schema mirrors normally omit those guards and describe the final schema state once. Always add indexes after their table and include `deleted_at IS NULL` in application reads for soft-deleted entities.

Application SQL belongs in `internal/repository/queries/`. Never edit `internal/repository/db/`; regenerate it:

```bash
make sqlc-generate
make sqlc-vet
```

Direct manual database changes are not part of the application workflow. Exercise behavior through migrations, tests, and API endpoints.

## Error contract

Every API error has a stable code and a request ID:

```json
{
  "error": {
    "code": "E02440001",
    "message": "document not found",
    "request_id": "c1e66a647ca6458fb34ad25c79bc29ab"
  }
}
```

Error codes use `E + Domain(2) + Type(2) + Sequence(4)`. For example, `E02440001` reads as document domain (`02`), not found (`44`), sequence `0001`.

| Domain | ID | Examples |
| --- | --- | --- |
| Common | `00` | malformed shared requests and fallback internal errors |
| Auth | `01` | invalid credentials, refresh tokens, and user lookup |
| Document | `02` | validation, ownership, not found, and state conflicts |
| Storage | `03` | invalid keys, missing objects, and provider availability |
| Queue | `04` | invalid jobs and Redis availability |

| Type | ID | HTTP meaning |
| --- | --- | --- |
| Bad request | `40` | 400 |
| Unauthorized | `41` | 401 |
| Forbidden | `42` | 403 |
| Not found | `44` | 404 |
| Conflict | `09` | 409 |
| Internal error | `50` | 500 |
| Service unavailable | `53` | 503 |

Constants live in `pkg/errors/codes.go`; their corresponding status, safe message, and retryability live in `pkg/errors/errors.go`. Add a new domain by reserving the next two-digit domain ID, defining unique constants, adding typed `AppError` values, and extending `codes_test.go`. Never reuse or renumber a published code.

Internal causes remain wrapped for application logging and error inspection but are never returned to clients.

## Tests and checks

The default test suite uses handwritten fakes and does not require PostgreSQL, Redis, S3, MinIO, or Docker:

```bash
make test
make vet
make lint
make sqlc-vet
make build
```

Tests are table-driven and parallel where shared state permits it. Generated SQLC code and thin `main` entry points do not need direct unit tests.

## Start a new repository from this example

1. Copy the entire `api_example` directory to the new project directory.
2. Run `git init` inside the copied directory.
3. Replace `github.com/example/api-example` in `go.mod` and imports, and replace the `api-example` application name.
4. Run `cp .env.example .env`, then replace secrets and infrastructure values.
5. Choose `STORAGE_DRIVER=local` or `STORAGE_DRIVER=s3`.
6. Run `make deps` and `make sqlc-generate`.
7. Run `make docker-up`, `make migrate-up`, and `make test`.
8. Keep the documents slice while implementing the first real domain, then remove it only after the new vertical slice covers every layer.

This directory deliberately has no nested `.git` directory. It remains tracked by the parent repository until copied out.

See [Architecture](docs/architecture.md) for layer and data-flow details.
